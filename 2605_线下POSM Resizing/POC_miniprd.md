# PoC 方案：线下 POSM 自动排版合成

> 状态：进行中 · 更新日期：2026-05-19 20:00

---

## 1. 背景与目标

线下 POSM 物料（海报、展架、陈列牌）在不同渠道/场地需要输出不同尺寸的版本。当前由人工在设计软件中逐一调整，效率低且易出错。

**PoC 目标：** 验证通过自动化流程完成"背景裁切 + 元素排版 + 合成输出"完整链路，实现一套输入素材 → 批量多尺寸 SVG+assets ZIP。

---

## 2. 技术路线

**结论：采用 SVG 路线**

| 维度 | PNG 路线 | SVG 路线（选用） |
|---|---|---|
| 资源消耗 | 高（2m×2m@200DPI≈ 1.5GB/张） | 极低（XML 文本操作） |
| 原始像素 | 裁切/合成后不可逆 | ✅ PNG 以路径引用保留，零像素损失 |
| 可编辑性 | 差（像素已拍平） | ✅ Illustrator 各图层独立可操作 |
| 成品框 | 像素描边，无法单独编辑 | ✅ 原生矢量 `<rect>`，独立图层 |
| 下游交付 | 直接交印刷厂 | 需在 Illustrator 导出 CMYK（标准印刷工作流） |

## 4. 处理流程

### 前置：训练集分析与规则提炼（AI 辅助，每活动一次）

> 这是整个流程的**前置环节**，不参与日常批量生成。每当有一套新的主底图和元素 PNG 进来时，执行一次，输出规则配置后固定下来。

**为什么需要这个环节：**  
排版规则本质上是比例和关系的集合（元素占画面多少、各元素之间如何联动）。这些规则可以从人工完成的参考稿中归纳出来，但如果靠设计师手动在 PS 里逐张测量，效率低且容易遗漏关联逻辑。

**AI 在这里做什么：**

| 任务 | 人工做法 | AI 辅助做法 |
|---|---|---|
| 解读参考稿的排版规律 | 设计师逐张在 PS 里测量元素位置、大小，制表归纳 | AI 直接视觉分析参考图，提炼元素间比例和位置关系 |
| 发现元素关联逻辑 | 人工对比多张图寻找共同模式 | AI 跨多张图归纳"主视觉参考→关联元素"的层级依赖关系 |
| 定位主体物视觉参考中心坐标 | 设计师在 PS 中手动标注并记录坐标 | AI 辅助推算，人工在 PS 中核验后确认 |
| 输出结构化配置 | 手工填写参数表 | AI 直接输出 `bg_config.json` 草稿，人工审核后上线 |

**本活动（Q2 广东社区媒体）训练集：**  
7 张参考稿（330~960mm 跨度），涵盖竖版、近方形、宽幅等比例。通过 AI 视觉分析归纳出的规则已固化到 `template/element_layout.py` 中。

**训练集分析报告（AI 输出，存档）：**

> 每次活动完成训练集分析后，Opus 输出的结构化报告存放于 `排版规则/` 目录，命名格式：`训练集分析报告_YYYY-MM-DD.md`。报告是 § 5.2 元素定位规则的直接 input——人工核验后将报告结论写入代码。

| 活动 | 报告文件 | 状态 |
|---|---|---|
| Q2 广东社区媒体（本活动） | [`排版规则/训练集分析报告_2026-05-18.md`](排版规则/训练集分析报告_2026-05-18.md) | ✅ 已核验并落地 |

**推荐使用的大模型：**

| 任务 | 推荐模型 | 理由 |
|---|---|---|
| 训练集视觉分析、跨图归纳元素尺寸/位置规律 | **Claude Opus 4.7 with Thinking**（`claude-opus-4-7-thinking-xhigh`） | 视觉推理 + 多图横向归纳 + 思维链能力强，能复现设计师"肉眼觉得不对"的判断逻辑，并产出结构化规则报告 |
| 把分析结论转化为代码 / 配置 JSON | Claude Sonnet 4.6（或同级编码模型） | 工程实现成本低、迭代快，配合 Opus 的分析结论改 `element_layout.py` 或 `element_config.json` 即可 |

> 实践经验：直接用 Sonnet 做视觉归纳容易给出"大致对但不够准"的结论；先用 Opus + Thinking 出结构化分析报告，再用 Sonnet 写代码，分工最高效。

**未来换活动时的预期耗时：** 提供新训练集图片 → Opus 分析 → 人工核验主体物视觉参考中心坐标 → Sonnet 落地 → 上线，全程预计 **30 分钟以内**。

```
Master BG  +  规格表（Excel）  +  元素 PNGs
    ↓
Step 1：读取规格
  openpyxl 解析 Excel → CitySpec（城市名、画布尺寸、成品框尺寸）
    ↓
Step 2：背景裁切 → assets/bg.png
  Template.crop_bg()：内容驱动锚点裁切，见 5.1.1
    ↓
Step 3：成品框定位
  居中对齐：trim_x = (canvas_w − trim_w) / 2
    ↓
Step 4：元素坐标计算 + 复制到 assets/
  get_can_canvas_pos()：从裁切参数推导罐心在画布中的绝对坐标（无需开图）
  Template.compute_layout()：基于成品框尺寸 + 罐心坐标，按 5.2 动态规则计算坐标
  shutil.copy()：元素原文件复制至 assets/，不修改像素
    ↓
Step 5：构建 SVG
  xml.etree.ElementTree，viewBox = 画布尺寸（px）
  所有 <image> 和 <rect> 附加 data-*-mm 属性（毫米调试信息）
    ↓
Step 6：打包 ZIP
  {城市}_{尺寸mm}.zip  ←  SVG + assets/
```

**异常处理：** Step 2/4 发生异常时整行跳过，全批次结束后输出异常清单。

## 5. 排版规则

### 5.1 基础规则

- **画布基准**：Excel 画面尺寸（大值）= 画布；可视尺寸（小值）= 成品框
- **成品框**：居中对齐于画布（四边等距内缩），矢量 `<g id="成品框"><rect/></g>`，最顶层
- **元素定位基准**：全部基于**成品框**，不基于画布边缘
- **禁止放大**：元素 PNG 禁止上采样；背景允许等比缩小（Lanczos）
- **背景与成品框解耦**：背景裁切逻辑不感知成品框，先裁背景，再叠矢量成品框

---

#### 5.1.1 背景裁切规则 ✅

> **Viewport = 画布尺寸**（与成品框无关）。  
> 从主底图裁出一个按画布宽高比的矩形，缩放（Lanczos）至画布尺寸，通过视觉参考中心坐标确保主体物落在目标位置。

**内容参考框（视觉定义）**

`5罐子+背景+helix+买点.png`（960×1110mm）定义了必须出现在画布内的内容：主体物（视觉参考中心）+ Helix + 买点文案。**它不是裁切尺寸参数，而是理解"什么内容要在画面里"的参照。**

![内容参考框](bg+bg扩展/5罐子+背景+helix+买点.png)

**训练集测量结论（6 张参考稿，330~960mm）**

| 指标 | 值 |
|---|---|
| 内容块（主体物左缘→文案右缘）占画布宽 | PoC 定稿 **90%** |
| 两侧边距 | 各约 **5%** |
| 主体物视觉中心垂直位置 | 画布高度的 **63.8%**（偏下） |

> 📋 **TODO**：90% 为 PoC 固定值，基于 328mm/420mm 画布视觉验证。未来接入更宽格式（580mm+）时需基于实际视觉验证重新校准，考虑动态 range。

**视觉参考中心坐标（`bg2000*2000.png`，200 DPI）**

> 每套主底图对应一份配置，描述主体物视觉中心在主底图中的位置，以及希望它落在画布中的目标位置。PoC 中主体物为奶瓶罐体。

| 参数 | PoC 值 | 说明 |
|---|---|---|
| 主体物中心在主底图 X | **6568 px**（≈ 834mm） | 15748×15748px 主底图 ⚠️ 待 PS/AI 人工核验（T-06） |
| 主体物中心在主底图 Y | **9183 px**（≈ 1166mm） | 同上 ⚠️ 待核验 |
| 主体物中心目标 X | 画布宽度的 **31.1%** | 主体物偏左，右侧留给 Helix+买点 |
| 主体物中心目标 Y | 画布高度的 **63.8%** | 主体物略偏下 |

**裁切公式**

```python
crop_w = CONTENT_REF_W_PX / CONTENT_FILL_RATIO  # ≈ 7299 px ≈ 928mm
crop_h = canvas_h_px * crop_w / canvas_w_px      # 按画布宽高比推导

crop_left = CAN_CX - round(crop_w * CAN_TARGET_X)
crop_top  = CAN_CY - round(crop_h * CAN_TARGET_Y)

output = bg.crop(...).resize((canvas_w_px, canvas_h_px), LANCZOS)
output.save(..., dpi=(200, 200))
```

**主体物画布坐标推导（`get_can_canvas_pos()`）**

由于裁切+缩放是线性变换，主体物视觉中心在画布中的位置可直接计算，无需开图：

```python
can_canvas_x = round(canvas_w_px * CAN_TARGET_X)   # 永远在画布宽度的 31.1% 处（PoC：罐心）
can_canvas_y = round(canvas_h_px * CAN_TARGET_Y)   # 永远在画布高度的 63.8% 处（PoC：罐心）
```

此坐标作为参数传入 `compute_layout()`，供辅助元素（PoC 中为"原装进口"印章）做动态避让定位。

**PoC 两城市裁切区**

| 画布 | 主底图裁切区（px） | 内容块占比 |
|---|---|---|
| 328×470mm 汕头 | 4217~11516 × 2273~13104 | 90% |
| 420×570mm 湛江 | 4217~11516 × 2631~12900 | 90% |

**异常**

| 触发 | 处理 |
|---|---|
| 裁切区 > 主底图任一边 | ⛔ 跳过，记录"主底图尺寸不足" |
| 锚点定位后裁切框超出边界 | ⛔ 跳过，记录"锚点裁切越界" |

### 5.2 元素定位规则（动态锚点与关系缩放）

> 元素定位采用**锚点父子依赖（Dom 树）**逻辑，而非简单的绝对画布比例。  
> 核心原则：先定标题 → 标题定顶部 Logo → 罐心辅助定 Icon → 底部组以标题宽为基准整组居中。  
> 所有元素禁止拉伸（强制等比缩放），超出成品框的计算结果自动压边。

> 📎 **本节参数来源**：由 Opus 对训练集图片进行视觉分析后，人工核验落地。详见 [`排版规则/训练集分析报告_2026-05-18.md`](排版规则/训练集分析报告_2026-05-18.md)。

元素定位包含三个维度，按以下顺序依次应用：

#### ① 大小（Size）

每个元素的尺寸以成品框宽或其他已知元素尺寸为基准，通过固定比例或测量比例推导，始终保持等比缩放。详见下方参数表。

#### ② 位置（Position）

**排版四步逻辑（设计师视角）：**

1. **确定标题位置**：标题是视觉主锚点，其上下边界决定上下半区的分界线。顶部距成品框 13%。
2. **放置顶部 Logo**：在标题正上方留约一个"标题行间距"的空间放置联合 Logo，两者共享水平中轴线。间距基于标题 PNG 内部行间距（10.4% 标题高）校准，补偿 PNG 顶部 8.8% 软 padding。
3. **处理底部元素组**：脚注（3）与右下角 Logo（4）作为**一组 Bottom Bar**，整体水平居中，垂直位置与顶部 Logo 上下对称留白。
4. **放置辅助标签**：原装进口 Icon（6）放在标题与罐体之间的左侧空间，参考罐心坐标动态定位。

#### ③ 避让策略（Collision Avoidance）

避让系统分两个层面：**元素兄弟互感知** 和 **元素 vs 背景主体物保护区**。

---

**层面 A：元素兄弟互感知（2026-05-19 新增）**

各元素并非完全独立定位——部分元素在确认自身尺寸/位置前，需先预算兄弟元素的占位边界，避免互相穿模。

元素优先级（谁固定、谁让步）：
```
底部组（对称规则锁死）> 印章（罐心锚定）> 标题（可等比缩放）> 顶部 Logo（跟随标题）
```

| 碰撞对 | 触发场景 | 让步方 | 策略 |
|---|---|---|---|
| **标题 ↔ 印章** | 画布短边偏小（≥150mm），标题按宽高比推算后下边缘压到印章 | 标题让步 | **Title Height Guard**：Step 1 完成后、写入 layout 前，预算印章顶边（`y6_prelim`）；若标题底边超出 `y6_prelim − 2% H`，等比缩小标题宽度直至满足约束。标题最小保留 5% H。 |
| **标题 ↔ 底部组** | 极矮画布 | 标题让步 | 同上约束链，标题压缩后底部组位置同步自适应（底部组由顶部 Logo 间距对称决定，而顶部 Logo 锚定标题上方）。 |
| **印章 ↔ 底部组** | 画布偏矮，印章下沉进底部组区域 | 印章让步 | Step 4 末尾独立检测：若 `seal_bottom > bottom_group_top − gap`，上推印章；floor = 标题底边。 |
| **印章上推 floor** | 印章被上推时不能压到标题 | 印章停止上推 | 所有上推逻辑均以 `title_bottom + gap` 为硬性下限。 |

**计算顺序（有约束传递）：**
```
① 预算印章顶边（罐心 × 0.73，临时值）
② 预算底部组顶边（对称规则，临时值）
③ 用 ①② 约束标题最大高度 → 等比缩放标题（Title Height Guard）
④ 从缩放后标题正式计算顶部 Logo
⑤ 从顶部 Logo 间距正式计算底部组
⑥ 正式放置印章 → 罐身碰撞检测 + 底部组碰撞检测（floor = 标题底边）
```

---

**层面 B：元素 vs 背景主体物保护区**

背景主体物（奶瓶）在画布中占据固定区域。当印章按罐心锚定规则放置后可能压入奶瓶标签区，影响产品展示。

**保护区定义（内部计算，不写入 SVG）**

基于 `bg_crop.py` 中已知的主体物视觉锚点（`CAN_TARGET_X=31.1%`, `CAN_TARGET_Y=63.8%`）与训练集缩略图目测测量（2026-05-18），推导出奶瓶瓶身的虚拟矩形保护区：

| 边界 | 公式 | 实测依据（425mm×575mm 缩略图） |
|---|---|---|
| 左边界 `protect_left` | `can_cx − 0.16 × canvas_w` | 瓶身左缘 ≈ 16.3% canvas_w，与 can_cx(31.1%) 差 ≈ 14.8%；取 16% 留安全余量 |
| 顶边界 `protect_top` | `can_cy − 0.24 × canvas_h` | 瓶身顶（盖/瓶体分界线）≈ 40% canvas_h；与 can_cy(63.8%) 差 ≈ 23.8%；取 24% |

**碰撞判断标准**

印章的**圆心 X**（`x6 + tw6/2`）是否进入保护区左边界，且印章底边是否低于保护区顶边界：
```
x_overlap = seal_center_x > protect_left
y_overlap = seal_bottom   > protect_top
```

使用圆心而非右边缘，是因为训练图中印章右缘天然略微压在瓶体左缘上（约 5% canvas_w），属于设计允许的正常叠压，不应触发避让。

**两阶段避让逻辑**

| 阶段 | 条件 | 动作 |
|---|---|---|
| Stage 1（上移） | `x_overlap AND y_overlap` | `y6 = max(protect_top − th6 − gap, title_bottom + gap)`（印章上移至瓶体顶界之上，但不低于标题底边） |
| Stage 2（左移） | Stage 1 被标题底边截停，y_overlap 仍存在 | `x6 = max(protect_left − tw6 − gap, ox)`（印章左移至保护区左侧，硬限：不超出成品框左边） |

极限情况（成品框非常紧贴奶瓶时）：两阶段均已执行但仍有部分叠压，此时印章已推至成品框左边缘且尽可能靠上，属于设计上可接受的退化降级。系统记录 DEBUG 日志供人工复核。

---

**当前实现参数（`element_layout.py`，基于 7 张训练图归纳 + PNG 像素扫描，2026-05-18 定稿）：**

| 元素 | 节点类型 | 宽度 | X 位置 | Y 位置 |
|---|---|---|---|---|
| 2 标题文字 | 主锚点 | 85% 成品框宽 | 水平居中 | 距成品框顶 13% |
| 1 顶部联合 logo | 标题伴生 | 标题宽 × 50% | 水平居中（同中轴） | 标题上方，gap = 标题高 ÷ 50（视觉间距 ≈ 标题行间距） |
| 6 原装进口 Icon | 独立辅助 + 避让 | 15% 成品框宽 | 左边距 3%（**碰撞时自动避让**） | 中心 = 成品框顶 + 罐心trim距 × **73%**（碰撞时上移） |
| 3 脚注 | 底部组左元素 | **由 group 目标宽反解**（≈72% W） | **整组水平居中** | group_bottom = trim_bottom − 顶部Logo上边距 |
| 4 右下角 logo | 底部组右元素 | **由 h4 + PNG宽高比反推**（≈12% W） | 整组右侧（内间距 2%） | 同组底边对齐 |

**底部 Group 规则：**
- `h4 = th3 × (432/727)`，其中 432/727 = 元素 3 fineprint ink bbox / PNG总高（像素扫描值）
- `tw4 = h4 × (744/431)`（元素 4 PNG 宽高比）
- `group_w = 标题宽 × 1.02`（group 比标题略宽，训练集实测）；`tw3 = (group_w − 2% W) / (1 + tw4/tw3系数)`
- `group_bottom = trim_bottom − (y1 − trim_top)`（底部留白 = 顶部联合 Logo 距成品框顶留白，上下对称）

---

### 5.3 元素缩放规则

- 目标宽度按上表百分比计算，等比推导高度（`h = orig_h × target_w / orig_w`）
- 原始宽 > 目标宽：等比缩小，SVG `width` = 目标宽，`height` 按比例自动算
- 原始宽 ≤ 目标宽：触发 `UpscaleError`，整行跳过

### 5.4 图层顺序（底 → 顶）

```
bg.png → 2标题无蒙版 → 6原装进口 → 1顶部联合logo → 3脚注 → 4右下角logo → 成品框
```

### 5.5 特殊说明

- 元素 2 使用**无蒙版**版本（`2标题无蒙版.png`）
- 宽幅格式（960mm+）元素比例规则不变，背景水平展示更多内容
- 罐心坐标通过 `get_can_canvas_pos()` 在每次处理时动态计算，不依赖视觉识别 AI

### 5.6 持续运营架构（已设计，PoC 后实施）

当前**背景锚点**与**元素布局参数**都写死在 `bg_crop.py` / `element_layout.py` 中，仅适用于本套主底图与本活动的 5 个元素。未来多活动运营时，计划引入**每活动配置文件 + 布局模板**双层机制：

```
活动目录/
├── master_bg.png
├── bg_config.json          ← 背景锚点参数（设计师 / AI 输出，约 1 分钟）
│     {
│       "can_cx": 6568,
│       "can_cy": 9183,
│       "content_ref_w_mm": 960.0,
│       "content_fill_ratio": 1.036
│     }
├── element_config.json     ← 元素尺寸 / 位置参数（AI 训练集分析输出，人工核验）
│     {
│       "layout_pattern": "vertical_poster_v1",
│       "elements": {
│         "title":       { "role": "anchor",   "width_ratio": 0.85, "y_ratio": 0.13 },
│         "top_logo":    { "anchor_to": "title", "width_ratio_of_anchor": 0.50, "above": true },
│         "footnote":    { "role": "bottom_group_left",  "width_ratio": 0.78 },
│         "rd_logo":     { "role": "bottom_group_right", "width_ratio": 0.19 },
│         "import_icon": { "anchor_to": "can",   "width_ratio": 0.15 }
│       }
│     }
└── elements/
```

**双层架构说明：**

| 层级 | 内容 | 变化频率 | 修改方 |
|---|---|---|---|
| **布局模板（pattern）** | 一种海报样式的代码实现（如 `vertical_poster_v1.py`），描述元素之间的依赖关系（标题 ← 顶 logo / 罐心 ← icon / 底部 group 居中）| 低（每种新版式新增一份，不动旧的）| 工程师 |
| **元素参数（element_config.json）** | 本活动元素的具体尺寸百分比、位置比例 | 高（每个活动一份） | 设计师 / AI |

**代码侧目录结构：**

```
template/
├── bg_crop.py
└── layout_patterns/
    ├── vertical_poster_v1.py    ← 当前 PoC 这套（标题居中 + 顶 logo + 底 group + 侧 icon）
    ├── horizontal_banner_v1.py  ← 未来横版广告（占位，按需新增）
    └── grid_v1.py               ← 未来网格布局（占位）
```

**工作流：**
1. 新活动来 → AI（Opus）分析训练集 → 判断"属于哪个布局模板"+ 输出 `element_config.json` 草稿
2. 人工核验配置 → 入库 → **不改代码**就能跑新活动
3. 如果出现完全没见过的版式 → 工程师新建一个 `layout_patterns/xxx.py`，**不动旧 pattern**

**为什么不用纯 JSON DSL 描述全部布局？**  
纯 DSL 灵活但实现成本高（需要自研规则引擎、debug 工具），PoC 阶段不值得；本方案在"参数化的轻量"与"扩展性"之间取折中。

**视觉识别 AI 运行时方案** 在此场景下性价比不高（每张图都跑模型 → 慢、不稳、贵），暂不采用。

### 场景 B：主底图尺寸不足 ✅ 已解决

裁切区 > 主底图边界 → `ValueError`，整行跳过。  
**解决**：已切换至 bg2000（15748×15748px），覆盖所有当前城市。

### 场景 C：锚点裁切越界 ✅ 已实现

锚点定位后裁切框超出主底图边界 → `ValueError`，整行跳过。  
（宽高比极端的格式如 330×558mm 在当前 CONTENT_FILL_RATIO 下可能触发）

### 场景 D：输入数据合法性校验 ✅ 已实现（2026-05-19）

前端（JS）与后端（Python）双层校验，任意一层触发均阻断生成。

**校验规则（`app.py`）：**

| 规则 | 条件 | 错误提示 |
|---|---|---|
| 最小尺寸 | 四个值均 ≥ 150mm | `{字段} {值}mm 过小，最小允许值为 150mm` |
| 竖版强制 | 画面高 > 画面宽；可视高 > 可视宽 | `尺寸必须是竖版（高 > 宽）` |
| 上限①：可视 < 画面 | `trim_w < canvas_w` 且 `trim_h < canvas_h` | `可视尺寸必须小于画面尺寸` |
| **下限：比例合理性** | `trim_w ≥ canvas_w × 80%` 且 `trim_h ≥ canvas_h × 80%` | `可视{宽/高}偏小（最小约 Xmm，即画面{宽/高}的 80%）` |
| **上限②：元素像素约束** | `trim_w ≤ TRIM_MAX_W_MM`（启动时由元素 PNG 自动计算） | `可视宽度超出上限（最大 Xmm）——元素 PNG 原始像素不足，放大会模糊` |

**下限 80% 的依据（来源：`FBB_【MR】APZA Y26 Q2 广东社区媒体(1).xlsx`，93 条有效数据）：**

| 维度 | 真实数据比例下限 | 绝对差上限 | 代码取值 | 安全余量 |
|---|---|---|---|---|
| 宽度 | 88.1%（≈ 0.881） | 80mm | **80%** | ~8% |
| 高度 | 84.4%（≈ 0.844） | 150mm | **80%** | ~4% |

> 取 80% 而非直接用观测下限，是为了容纳未来新媒体类型出现略大出血量的情况，同时拦截 `canvas=300, trim=50`（比例 17%）等明显错误输入。  
> 常量 `TRIM_MIN_RATIO = 0.80` 在 `app.py` 中统一维护，前后端共享同一语义。

**上限②（元素像素约束）的计算方式：**

服务启动时读取 `png元素/` 目录下所有元素文件，结合 `element_layout.py` 中各元素占成品框宽的比例，推导每个元素允许的最大 `trim_w`，取最严格约束值（当前由 `title.png` 决定）：

| 元素 | 原始宽 (px) | 布局比例 | 最大 trim_w (mm) |
|---|---|---|---|
| `title.png` | 4377 | 85% | **653** ← 当前约束 |
| `top_logo.png` | 2221 | 42.5% | 664 |
| `footnote.png` | 4393 | 72% | 775 |
| `corner_logo.png` | 744 | 12% | 787 |
| `imported.png` | 997 | 15% | 844 |

> 此上限随元素素材自动更新——换用更高分辨率的 `title.png` 后，重启服务即可解锁更大尺寸，无需改代码。  
> 常量 `TRIM_MAX_W_MM` 在启动日志中打印：`元素像素约束：成品框宽度上限 = 653 mm`。
